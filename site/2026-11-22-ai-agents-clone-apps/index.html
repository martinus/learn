How AI agents copied Photoshop and Office

In autumn 2026, the developer Brandon Thomas let AI programs write copies of Photoshop, and then of Word, Excel and PowerPoint. The first large version of the Photoshop copy came three hours after the start. This page shows how he set up the AI agents, how the project works now, what measurements say about the structure of the code, and what you can learn from it. You need no knowledge of programming.

Status: early test versions, much work in progress The copies are free and open source. The project calls them “early alpha”. It says itself that the Photoshop copy cannot replace Photoshop for daily professional work yet. All counts on this page are from 22 November 2026. They change every day.

The method

First a plan, a rule file and a checklist of all menu items. Then many AI agents worked at the same time, and automatic checks stopped bad changes.

The quality

Many functions exist, and real files open. But an independent measurement rates the inner structure of the code far below average.

The lesson

Rules that a program checks hold. Rules that are only text get lost. Fast-growing code needs regular tidying, also when an AI writes it.
01

What exists today

Brandon Thomas leads the project ArtCraft. Its apps are copies of well-known programs, which the news calls clones: PhotoCraft (Photoshop), WordCraft (Word), GridCraft (Excel) and DeckCraft (PowerPoint). All are written in the programming language Rust. Anybody can read and use the code.

The history of the code is public. Each saved change is a commit, with a time and an author. From this history you can follow the project step by step:

  2. 30 Sep, 09:02 UTCA commit with the name “one-shot” adds 241 files with 42,241 lines of code.

  4. 6 OctStart of WordCraft, GridCraft and DeckCraft, and of a shared library for all apps.

02

A plan before the code

An AI agent is a program that uses an AI model to do a task in many steps. It reads files, writes code, runs tests, reads the errors and corrects them. Thomas used Claude Code, an agent by the company Anthropic, without special additions. He wrote on Hacker News: “We're using vanilla Claude Code”. Of the commits that name an AI model as co-author, most name Claude Opus 5.5.

The prompts are not public. The plans are in a folder that the project keeps private. Thomas says, as BigGo reports, that the first working state came after about 24 hours, from one large and structured prompt. The first commit shows the result of the planning: three things that tell each agent how to work.

  • A rule file for agents (AGENTS.md). It says what to read first, seven “golden rules”, and which checks must pass before a task is finished.
  • An architecture plan. It divides the program into parts in seven layers. It also names lessons from the free image editor GIMP: GIMP needed many years to change basic assumptions, for example about colour depth. PhotoCraft treats such properties as data from the start.
  • A checklist. On the first day, the full menu tree of Photoshop came into the code as a list. Each entry has a fixed name, and a small program counts how many entries already work. The news site Declic reports how the team got the list: it installed Photoshop and listed the contents of the package without starting the program, for example shortcuts, plug-ins and texts from the program file. The first plan also used the menu tree of a different image editor, Photon Studio, with 720 items, as the list of work.

A comparison: a large kitchen with many cooks. The checklist is the menu card. The architecture is the plan of the stations. The rule file hangs on the wall. The tests taste each plate before it goes out. The comparison has a limit: cooks talk to each other. Agents know only what is in the files.

The most important rule of the architecture is the direction of the layers. A part may use only parts in lower layers. The user interface may use the engine, but the engine may not use the user interface. A program checks this at each change. Select a layer:

A second rule is just as important: everything is a command. Each action has a fixed name, for example filter.blur.gaussian. The menu, the keyboard, the tests and other AI agents all start the same command. The agents use a standard connection with the name MCP. So an agent can test each function without a screen. It can also start the app, click, take a screenshot and look at it.

03

Many agents at once

On 2 October an agent wrote an estimate into the project. It says that one session finished about 70 menu items and large parts “using 8 parallel agents”. Eight agents worked at the same time. For this, the rule file had a special rule. Each agent builds in its own folder, so that the agents do not block each other. And each agent changes only the parts that are its own.

The Office copies used the same pattern. WordCraft started on 6 October at 00:23 UTC. In the next three and a half hours, commits named after the steps of a plan (“M0.1” to “M1”) added a document model, more than 200 commands, a user interface with all ribbon tabs, an MCP connection, and reading and writing of Word files.

Why was this so fast? Copying a known program is an unusual task. The goal is fully known. You can split it into hundreds of small tasks, and you can count the progress. Each small task has a clear test: does it do the same as the original? This is the situation in which AI agents are strongest.

A comparison: to build a copy of an existing house is faster than to design a new one. You can measure each room of the original. You do not have to decide what the house is for.

The work flow changed after the first weeks. Compare the two states:

One step needs an explanation: the clean room. This is a method to copy a product without copying protected work. One team studies the original and writes only a description of its behaviour. A second team writes the code from this description and never sees the original. Critics on Hacker News said that it is not a clean room if the same AI uses Photoshop and writes the code. Since 18 November, a project rule forbids this. It also forbids reading anything inside the installed package of the original. The legal questions are open. This page does not judge them.

04

From one person to a community

After the first week, Thomas looked for help. On 5 October he wrote that he needed a community for bug reports and code changes. Many people came. A proposal of the project says that much of their work comes from coding agents. The chart shows the commits per week. Select an app:

In PhotoCraft, Thomas made only 6 of the commits since 1 November. On 2 November he wrote of “about 50 core developers”, with one responsible person for each area. The history shows a new role for him: direction, community and decisions, and less own code.

Around the apps, the project built a structure that a large software company would also have:

  • A project for rules (craft-contrib). Changes to the rules need a written proposal and a decision, as in large open-source projects. Before, the same rule had up to 20 different wordings in 28 public repositories. In November the project decided on one shared rule file for agents. PhotoCraft uses it since 20 November.
  • A shared library (craft-libs). Parts that all apps need, for example readers for file formats, are in one place.
  • Review by programs. The service CodeRabbit comments on each proposed change. The service SonarCloud scans the code for errors.

The proposals for the rules show what went wrong. An agent follows its instructions literally, so a gap in them becomes the same error many times: two agents fix the same bug, or an agent uses functions that do not exist. The answers are simple rules: claim a task first, open each definition before you use it, keep each change small, and read your own change before you send it.

The models also change. About 6,000 commits in PhotoCraft name Claude Opus 5.5 as co-author, some name other models. The real share of AI is not known, because not every author names the model. For some weeks in November, a project rule even said that a pull request must not say that an agent wrote it. On 1 November Thomas wrote that he now plans with Claude and lets the open model Kimi write the code.

05

How good is the code?

Quality has two sides. The first: does the program work for the user? The second: is the code inside built so that people can change it safely? A program can be good on one side and bad on the other.

For the user, the project gives an honest picture itself. In mid-October it had 953 open reports about bugs and missing functions. Its roadmap of October says that it missed most speed targets, and that Photoshop did not reliably accept the files that PhotoCraft wrote. In early October, testers on Hacker News reported slow controls, broken text editing and shortcuts that did nothing. Another tester built the app and found it mostly in order.

For the inside, there is one independent measurement. The Dutch company Software Improvement Group (SIG) examined the seven Adobe copies, in the state of 12 October. SIG gives stars from 0.5 to 5.5. Three stars is the average of the market. Four stars is the target that SIG recommends for new software. Select a measure:

Security is good, also because the language Rust prevents many typical errors. Maintainability and architecture are weak. Single functions are weak too, but SIG finds the largest problem in the connections between the parts. In PhotoCraft, the value for modularity is 0.7 stars. SIG calls the picture of the architecture “spaghetti-code”: too many parts depend on too many other parts. A change in one place can break something in a different place.

Thomas does not see this as a big problem. On 2 November he compared code with DNA, which is not designed cleanly either: “Evolve it, don't intelligently design it”. Tests remove bad behaviour. SIG answers that such code makes each later change slower and more expensive, also for agents, because they must read more of the code. This page does not decide between the two positions.

06

Where the structure bends

For this page, the code of PhotoCraft was counted on 22 November. The result shows both: what the plan protects, and what it does not protect.

The direction of the layers holds, because a program checks it. But this check does not look at the size of the layers. Look where the lines of code are:

The two top layers, the engine and the user interface, contain 547,000 of 873,000 lines: almost two thirds. The base layers are small. There is a reason for this. The checklist counts menu items. Each menu item becomes a command in the engine, and often a dialog or a panel in the user interface. So most new work lands at the top, whatever the plan says about the layers.

The same happens inside single files. Some files are central: almost each change touches them. The chart shows two of them. Move the date:

The file for the drawing surface grew from 1,240 to more than 10,000 lines in less than four weeks. On 26 October, a contributor reorganised the user interface. The file grew again. On 17 November it became small again for a different reason: PhotoCraft moved large parts of its user interface into a shared framework in the shared library. The code moved. It did not disappear.

A comparison: a drawer in a kitchen. Each new thing goes into the drawer that is already open. For some time this works well. Then you can find nothing, and somebody must empty the drawer and sort it. The agents put each new function where the code that they had just read was.

This is not special to AI. In 1980 the computer scientist Meir Lehman described it as a law: a program that people change becomes more complex, unless somebody works to reduce the complexity. Agents only make it happen faster. Also, to divide a file does not reduce the connections between the parts, which SIG measured.

07

How the structure can stay good

The project already protects its structure in several ways. This list shows what the published code contains on 22 November, and what is missing:

  • In placeA check for the direction of the layers.Since the first large commit on 30 September. It runs at each change.
  • In placeEach action is a command, and panels may change data only through commands.A check finds panels that go around the commands.
  • In placeA limit for the complexity of one function.The Rust tool Clippy stops functions that are too complex.
  • In placeTests are necessary, and nobody may delete or weaken a test to make a check pass.Rule in the shared rule file.
  • PartlyShared parts come from the shared library, not from copies in each app.A rule since 17 November. Copies from the first weeks must still move.
  • Not foundA limit for the size of files, parts and layers.I found no such check. The data of section 06 shows why it would help.
  • Not foundA limit for the connections between parts.SonarCloud scans the code, but I found no check that stops a change when the parts become more tangled.

Software architects call such automatic checks fitness functions: each goal for the structure becomes a test that runs at each change. The rule of the layers is a good example. From the facts on this page, these ideas follow. They are suggestions of this page, not plans of the project:

  1. Make each structure goal a check. For example: no file larger than 2,000 lines, a maximum share for each layer, a limit for the connections of each part. Text rules get lost when many agents work. Checks do not.
  2. Tidy up on a schedule, not in an emergency. The central files were divided only at more than 10,000 lines. A weekly agent that divides the files with the most changes is cheap.
  3. Give the structure an owner: an agent or a person who reads each change only for the structure, and who can say no.
  4. Divide the top layers further, for example one module for each area of functions, each with a responsible person.
  5. Measure behaviour, not only connections. “664 of 664 menu items” counts connections. The project has started to do more: according to Declic, tests compare the pictures of PhotoCraft with more than 250 files that scripts made with the real Photoshop.
  6. Save work and money. Start new apps from the shared library. Let a strong model plan and a cheaper model write the code, as Thomas does now. Let agents claim their tasks, so that no work is done twice.
08

What you can learn for your work

If you use Claude Code or a similar agent, you can use the same pattern in a smaller size:

  • Write the plan and the rules first: a rule file (CLAUDE.md or AGENTS.md) with the structure, the test commands and what is forbidden.
  • Give the agent a list that it can count. A checklist makes progress measurable.
  • Let programs enforce the rules: tests, lint tools and a check of the structure, at each change.
  • Make each function a command, so that the agent can test it without a screen.
  • Run agents in parallel only on separate parts, each with its own build folder.
  • Keep the human work for direction, review and tidying.
  • Know the limit of the example. A copy has a known goal and a natural checklist. A new product has neither, so it needs much more planning.

Terms

AI agent
A program that uses an AI model to do a task in many steps: read, write, test, correct.
Open source
Code that is public. Anybody may read, change and pass it on, under the terms of its licence. Open Source Initiative: the definition
Alpha version
An early test version of a program. It is not complete and has known errors.
UTC (Coordinated Universal Time)
The time standard of the world. Austria uses Central European Time (CET), which is UTC plus one hour, and in summer Central European Summer Time (CEST), UTC plus two hours.
Rule file (AGENTS.md, CLAUDE.md)
A text file in a project that an AI agent reads before it starts: the structure of the code, the commands for the tests, and what is forbidden. AGENTS.md and CLAUDE.md are common names for it. AGENTS.md: the format
Rust
A programming language for fast programs. Its rules prevent many typical errors with memory before the program runs. The Rust website
Commit
One saved change in the history of the code, with a time and an author.
Roadmap
A plan of a project: its goals, and how far the project is with each goal.
AI model
A program that learned from very large amounts of text and code. It answers an instruction with text or code. Claude Opus 5.5 and Kimi are AI models. Wikipedia: Large language model
Prompt
The text instruction that a person gives to an AI model.
Architecture
The division of a program into parts, and the rules for how these parts connect.
Layer
A group of parts of a program. A part may use only parts in lower layers.
Engine
The core of a program that does the work, without the user interface. In PhotoCraft, it holds the open documents and the list of all commands.
Command
One action of the program with a fixed name. Menu, keyboard, tests and agents all start the same command.
MCP
Model Context Protocol: a standard connection through which an AI agent can operate a program. The MCP website
Build
The step that turns the code into a program that a computer can run. The build writes many files into a folder.
Test
A small program that checks automatically that a part of the code does what it should. A project runs its tests at each change.
Clean room
A method to copy a product: one team describes the behaviour, a second team writes new code only from this description. Wikipedia: Clean-room design
Merge commit
A commit that joins two lines of work, for example a proposed change and the main version.
Repository
A folder of code together with the full history of its changes. Projects often keep it on a website such as GitHub.
Library
Code that several programs share. A program uses its parts instead of writing them again.
Pull request
A proposed change to the code. People or programs review it before it goes into the main version.
Open model
An AI model that anybody may download and run on their own computers.
SIG (Software Improvement Group)
A Dutch company that measures the quality of code and sells such analyses. It rates code with stars from 0.5 to 5.5.
Maintainability
How easily and safely people can change the code.
Modularity
How well a program is divided into parts with few connections between them. With good modularity, a change in one part does not break a different part.
Framework
A library that gives a program its frame. The program fills in its own parts.
Fitness function
An automatic check for a goal of the architecture. It runs at each change.
Lint tool
A program that reads code and warns about suspicious patterns before the code runs. Clippy is the lint tool of Rust.
